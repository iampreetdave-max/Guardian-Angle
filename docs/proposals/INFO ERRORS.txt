  🔴 Critical — the users table

  Three policies combine into a likely privilege-escalation + data-integrity hole:

  users_delete   (DELETE, authenticated)  USING: true          ← any logged-in user can delete ANY user
  users_insert   (INSERT, authenticated)  WITH CHECK: true     ← any logged-in user can insert ANY user row
  users_no_delete(DELETE, public)         USING: false         ← intended to block deletes...
  users_update_own(UPDATE, public)        USING/CHECK: auth.uid()=id   ← update your own row, no column limits

  Why this is serious:
  1. Delete-any-user: users_delete grants USING true to authenticated. The users_no_delete (false) policy does not save you —
  permissive policies combine with OR, so true OR false = true. So unless users_no_delete is marked RESTRICTIVE (my query didn't
  capture that column — needs checking), any employee can delete every user row. The very name "users_no_delete" suggests someone
  thought they were blocking deletes but it only works if it's restrictive.
  2. Self privilege-escalation: users_update_own lets you update your own row with no column restriction. The role column is
  unprotected. Since is_super_admin() / current_user_role() read users.role, an employee can likely run UPDATE users SET
  role='super_admin' WHERE id = <self> and become super_admin — which unlocks nearly every admin policy in the whole schema. (Caveat:
  a BEFORE UPDATE trigger could block role changes — must verify.)
  3. Insert-arbitrary-users: WITH CHECK true lets any authenticated user inject users rows, including ones with role='super_admin'.

  This is the headline. You (preet.d, role employee, status training) can probably escalate to super_admin.
