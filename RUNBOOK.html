Common questions

The 15 you are most likely to get. Short enough to say out loud. The uncomfortable ones are answered honestly on purpose — a judge who catches you hedging stops believing the rest.

Is this real crime data?
No, and we say so on every slide. It is fully synthetic and deterministic — generated from a fixed seed, no real individuals named anywhere. Ahmedabad publishes no per-neighbourhood crime dataset, so the alternative was inventing numbers and calling them real. The locality weightings are editorial estimates and documented as such.
What database?
SQLite for everything relational — 34 tables, no ORM, plain sqlite3. FAISS for vectors, in three separate indexes. ChromaDB for the legal RAG. FAISS stores vectors and returns an ID; SQLite turns that ID into a camera, a timestamp and a thumbnail.
Why SQLite and not Postgres?
It has to run on a police station machine with no internet and no DBA. Three files in a Docker volume, one compose command, done. The trade-off is real: SQLite is single-writer. That is fine at station scale, and because there is no ORM coupling, moving to Postgres and pgvector is a swap of the database and index layers, not a rewrite.
What models, and do you need a GPU?
No GPU. Everything is CPU: torch 2.5.1+cpu, CUDA unavailable. Four models do the work — CLIP ViT-B/32 for text and image embeddings, YOLOv8n for detection, ArcFace/InsightFace for faces, and MiniLM for the legal RAG. YOLOv8n is 6.3 MB; the nano variant was chosen deliberately because detection runs on every keyframe of every camera, on CPU.
Search feels fast for a model — what is actually happening?
Search never runs a vision model. All the expensive work — CLIP, YOLO, ArcFace — happens once at ingest. A query only embeds your sentence and does a FAISS lookup. Warm text search measures 37 to 80 ms.
How accurate is the search?
84.6% recall on a hand-labelled ground-truth set, measured at the top-60 the UI actually uses. An earlier number of ours was lower because it was measured at top-20, which is not what the product does — we corrected it.
How accurate is the prediction?
Hit-Rate@10 of about 0.78 and PAI@10 of about 2.34, from rolling-origin cross-validation with bootstrap confidence intervals, against an oracle ceiling so you can see how much headroom is left. It is a backtest on synthetic data — it demonstrates the methodology is sound, not that the model predicts real Ahmedabad crime.
Isn't this just off-the-shelf models glued together?
The models are off the shelf and we do not pretend otherwise — that is the correct engineering decision, not a shortcut. The work is in what sits between them: per-detection crop embeddings so 'red car' can find one specific car, tracking so repeat sightings collapse into one result, and the honest evaluation harness. Anyone can call YOLO. Fewer people ablate their own scoring function and publish that two of its three terms contribute nothing.
What is genuinely novel here?
Three things. Per-object CLIP retrieval, which lets a query exceed the detector's own vocabulary — YOLO has no class for 'red'. The closed loop from footage to evidence to a drafted legal instrument. And measured validation with the negative results left in.
What does not work?
CLIP cannot do negation — 'empty street with no people' returns the busiest scene, because the model has no operator for 'no'. Hindi and Gujarati documents render malformed as PDFs because ReportLab does no Indic shaping; the interface is fully translated but the PDF body is not. And face matching degrades on low-resolution CCTV, which is most real CCTV.
Does it scale? You have 16 cameras, Ahmedabad has thousands.
Honestly: not as it stands. Ingest is the bottleneck, and ultralytics is not thread-safe — we measured 7 of 8 concurrent threads crashing, so there is a global inference lock that caps throughput. The upgrade path is per-thread model instances and a worker queue, and the ceiling is named in a comment in the code rather than hidden.
What about privacy and misuse? This is face recognition on public CCTV.
It is the right question to ask. Face search is scoped to footage already lawfully held, every search is written to an audit log, access is role-based, and nothing leaves the machine — no cloud inference, no API keys, no telemetry. It is a tool for an investigator working an existing case, not a surveillance dragnet, and the offline-first design is part of that argument rather than incidental to it.
What would it cost to deploy?
Effectively the hardware already in the station. No GPU, no per-query API cost, no cloud bill. That is the whole point of running CPU-only and offline.
Why offline-first?
Because station connectivity is unreliable and evidence should not leave the building. The hosted link is a convenience for you to click; the product is designed to work with the network unplugged.
How long did this take, and what is the code like?
The interesting number is not lines of code. Six demo-breaking bugs were found and fixed by testing rather than reading — four of them were failing silently behind HTTP 200s. The evaluation harness exists specifically so claims can be checked rather than asserted.

If they ask

Why do a wrong password and an unknown email give the same error?
Deliberate anti-enumeration. If the messages differed, the login form becomes an oracle for discovering which email addresses have accounts — useful for targeting officers with phishing. The same rule is applied to the forgot-password flow, which returns 'If the email exists, a reset token was sent' regardless. Both responses come back on the same path in comparable time, around 2.5 seconds.
You're showing real passwords on the login screen. Isn't that a problem?
Yes, and it's gated for exactly that reason — the panel is dev-only demo seeding, and the seed module is explicit that these are DEV ONLY credentials controlled by a settings.seed_demo_users flag. It exists so judges can drive four roles without waiting on us. For any real deployment the flag is off, the accounts don't exist, and the panel doesn't render. I'd want to see that verified in the deployment checklist rather than take it on trust.
How are sessions handled — JWT, cookies, refresh tokens?
A bearer JWT in localStorage, injected by an axios request interceptor. The payload carries sub, role, an exp and a tv field — token_version — which is the revocation mechanism: bump the user's token_version and every outstanding token for them stops validating. There is no refresh token; when the JWT expires you sign in again. A response interceptor drops the token and reloads on a 401, deliberately excluding the login call itself so a wrong password doesn't cause a reload loop.
What stops someone brute-forcing these logins?
A token-bucket rate limiter keyed on (IP, route class): 10 requests per minute for auth routes, 120 for the general API, 20 for uploads, with a Retry-After header on the 429. Worth flagging for tomorrow specifically — it's per IP, so if several judges try the demo accounts from the same conference wifi behind one NAT, they share the 10/min budget and will start getting locked out. If more than two people will be logging in at once, that number wants raising before the session.
What is the single worst bug on this screen?
Registering with a password shorter than six characters white-screens the entire application. The server correctly returns 422, but FastAPI's 422 body puts detail as an ARRAY of validation objects, and the client does setError(err?.response?.data?.detail || ...) and renders it — React refuses to render an object as a child and throws error #31, which unmounts everything to the ErrorBoundary. Only a Reload button remains. The same pattern exists at 15 call sites, and I confirmed a second demo-reachable one: Admin → Add staff user with a short password crashes identically. The root-cause fix is two lines in the axios response interceptor that already exists in frontend/src/api.js — normalise an array-shaped detail into a string once, and all 15 sites are fixed. I did not apply it because other agents are testing this stack and it needs a frontend rebuild.
Can I reset a password with no mail server?
Yes, that's what the 'Offline demo' wording is about. Forgot password generates a token; instead of relying on SMTP it tells you to read it from the admin outbox or the server log, then paste it into the 'Have a token?' form. The whole platform is built to run air-gapped — same reasoning as Arbiter's offline mode and the bundled legal corpus — so the auth flows had to work without outbound mail too.

If they ask

Is "417 indexed frames" a database row count or the actual search index?
The actual index. analytics.py imports get_clip_index() and reads .ntotal off the running FAISS object — it is the only KPI on this page that does not come from SQLite. It happens to equal COUNT(*) FROM frames (417) right now, which is the correct invariant: every extracted keyframe got embedded.
2,001 complaints — is that real Ahmedabad crime data?
No, and we say so on the City Map footer and in docs/AHMEDABAD_CRIME_DATA.md. It is a deterministic synthetic 180-day stream generated from public NCRB/press-derived area profiles (seed_synthetic.py, fixed RNG seed). The 9 cases, 30 evidence items and 5 ratings on this screen are real actions taken through the real UI.
How is "avg resolve 115h" computed?
AVG((julianday(closed_at) - julianday(created_at)) * 24.0) over cases WHERE status='closed' AND closed_at IS NOT NULL. Cases still open contribute nothing, so it is a survivor-biased number by construction — it answers "how long did the ones we finished take", not "how long does a case take".
Open 4 + closed 6 = 10 cases, but 2,001 complaints. Where did the other 1,991 go?
Complaints and cases are different entities. A complaint is a citizen report; it becomes a case only when an officer triages and converts it. The complaints-by-status chart shows exactly 9 in state 'converted' — those are the ones that became cases. The other 1,992 sit in submitted (809) / under_review (799) / assigned (384). That ratio is deliberate: it is what a real station backlog looks like.
What charting library is this?
None. charts.jsx is 104 lines of hand-written SVG and CSS — three primitives (BarList, Donut, TrendBars). No Chart.js, no Recharts, no CDN font or script. The whole page renders with the network cable pulled, which matters for a police intranet deployment.
How live is "live"?
15-second poll of /api/analytics/summary — I measured exactly one extra request in a 17-second window. It is polling, not websockets; that is a deliberate choice because the numbers are aggregates that change on the order of minutes, and polling survives a proxy that kills long-lived connections.

If they ask

VisionScan has Text search and Object search — what is the difference?
Text embeds the WHOLE FRAME with CLIP and finds scenes: one 512-d vector per keyframe, cosine-matched against the embedded sentence. It answers "where does this situation happen". Object runs a YOLO label filter over the detections table first, and when the phrase isn't one of YOLO's classes it falls back to per-detection CLIP on the cropped object regions — that's what lets "red car" find a specific car and draw a box on it. Concretely on this data: plain text "red car" returns 1 fuzzy scene; per-object returns 24 individually-boxed cars.
What does "Grouping moments" actually do?
Two different things depending on the search, and that is deliberate. For text, YOLO-label and face search it clusters frames from the same camera that are within event_gap_sec (6 s) of each other and keeps the highest-scoring one as the representative — so 40 raw frames of one person loitering become 8 distinct moments. For per-object (region) search it groups on track_id instead, because two different red cars visible in the same second are two results, not one; time-clustering would wrongly merge them.
Those scores are only 25–33%. Is that a bad match?
Those are raw CLIP cosine similarities, and for text-to-image CLIP the usable range is compressed — roughly 0.18 is noise and 0.33 is a strong hit on this data. What matters is the ranking and the relative floor: we cut anything below 0.22 absolute and below 0.88× the top hit. That is why "underwater coral reef scuba diver" returns zero instead of a page of 0.20s. We do not present the raw number as a confidence probability.
Can it handle negation — "a street with NO people"?
No, and this is a real limitation of CLIP, not a bug in our code. CLIP has no logical operators; it embeds the bag of concepts, so "no people" pulls toward frames about people and streets. Measured: "empty street with no people" returns 5 hits and all 5 contain detected people. Worse, per-object "no people" returns 60 hits topped by stop signs and a fire hydrant. The honest workaround is structural, not semantic: use Object search for "person" with grouping on and read the frames where the count is zero — the detections table can answer absence, the embedding cannot.
How large is the index, and would this scale to a real city?
Right now: 417 keyframes, 3,362 detections, 956 faces, 1,409 tracks across 16 cameras, in FAISS with SQLite for metadata. Warm text search is 80 ms median. FAISS flat search is linear, so at city scale you would move to an IVF or HNSW index and shard by camera or time window — the retrieval layer is already abstracted behind get_clip_index(). The honest gap is ingestion, not search: we index at roughly 2 keyframes/second of footage on CPU, so real-time coverage of hundreds of cameras needs GPU workers, not a different algorithm.
Why keyframes and not every frame?
Keyframe sampling at ~2 fps. Every frame would multiply the index ~15× for almost no recall gain, since consecutive frames are near-identical — that is the same redundancy the grouping toggle exists to hide. The cost is that fast-moving objects can be missed between keyframes, which is exactly what the Scene Analytics quality badge reports per camera.

Careful / known limits

  • CLIP cannot do negation. "empty street with no people" returns 5 hits and every single one contains detected people (2, 1, 3, 1, 1). The often-repeated phrasing that it returns "the busiest scene" is an overstatement — the top hit has 2 people, while the crowded-market top hit has 7 — so do not say that on stage. The defensible line is: "CLIP has no NOT operator; every frame it returned still contains people." The sharper illustration if a judge pushes: per-object search for "no people" returns 60 hits led by stop signs and a fire hydrant.
  • "Find every object" hides the "Grouping moments" toggle and the state leaks across tabs. If they ask

What happens when I type something YOLO has never heard of?
The UI tries the exact label filter first. If that returns nothing, it automatically re-issues the query against the per-detection CLIP index — every detected object crop has its own embedding, 3,355 of them — and labels the result banner "not an exact object label — showing per-object visual matches (CLIP) instead". So "red car" works even though YOLO's 80 classes contain "car" but no colours.
Why does grouping give 24 but ungrouped gives exactly 60? That looks like a round number.
Good catch — 60 is a cap, not a total. The UI requests top_k=60 for per-object search. If you raise it, 78 crops pass the relevance filter and collapse to the same 24 tracked objects. So the honest statement is: 78 individual detections match, showing the first 60, which are 24 distinct physical objects.
How do you know two detections are the same car rather than two cars?
We do not guess from time or position — we use the track_id the tracker already assigned during ingestion, grouping on (video_id, label, track_id). That matters: two different red cars visible in the same second are two results, not one, which naive time-clustering would wrongly merge. Detections with no track_id are deliberately left ungrouped rather than lumped together, since we cannot know.
That top hit is labelled "truck" but it is clearly a car. Is your detector wrong?
Yes, on that instance. YOLO mislabels some vehicles in this footage, and we surface the label rather than hiding it. It matters less than it looks, because the per-object CLIP fallback ranks on the visual embedding of the crop, not on the label — that hit surfaced because the crop looks like a red car, regardless of what YOLO called it. The label chip is shown so the operator can see and discount the disagreement.
Can this ever return nothing when nothing matches?
The YOLO-label path can — an unused label returns zero. The per-object CLIP path effectively cannot, and that is a real weakness: the absolute floor is 0.22 but object crops sit at a higher noise floor, so "elephant in a swimming pool" still returns 13 cars and people. The whole-frame text path does return zero correctly. If a judge wants to see an honest empty result, use Text search, not this tab.
Is the bounding box computed at search time or stored?
Stored at ingestion, in the video's native pixel space, then converted to fractions of the frame at query time so the box lands correctly on a thumbnail scaled to a 480 px long edge. Rows from before that migration emit no box at all rather than a wrong one — a wrong box on evidence is worse than no box.

If they ask

Is this just image hashing or a pixel diff?
No — it is a CLIP image embedding, the same 512-d space the text queries land in. I proved it by feeding a probe that was cropped to 75%, downscaled to 320 px and re-encoded at JPEG quality 45; a hash would have missed entirely, and it still matched at 0.86. What it matches is scene composition and semantics, not bytes.
Why did the red-car crop return nothing?
Because this tab compares your image against WHOLE FRAMES, and a tight crop of one object has a completely different global composition from the wide street scene it came from. It scored 0.6887 against a 0.72 minimum. That threshold is deliberately high — for reference-image search a false positive is worse than an empty result. The right tool for an object crop is the per-object search on the Object tab, which compares crop-to-crop.
Why is the threshold 0.72 here but 0.22 for text?
Different modalities, different score distributions. Image-to-image CLIP similarity is naturally high — two unrelated street scenes already sit around 0.6 — so a meaningful match has to clear 0.72. Text-to-image similarity is compressed into a much lower band, where 0.3 is already a strong hit. Using one threshold for both would either flood the image results or silence the text results.
What is the false positive rate?
On the one probe I measured: zero. 22 hits returned, all 22 on the correct camera, none of the other 15 cameras or the remaining 395 indexed frames surfaced. That is a single-probe result on a 417-frame index, not a benchmark — I would not quote a general accuracy number from it.
Could an officer upload a suspect's photo here instead of the Face tab?
They could, and they should not. This tab embeds the whole image, so a portrait would match other portrait-like frames by composition rather than identity. Identity matching is the Suspect Face tab, which runs ArcFace on detected faces. I tested exactly this crossover: the face crop uploaded here returns 0 matches, which is the correct refusal.

If they ask

What model is doing the face matching, and why not CLIP?
ArcFace, via InsightFace, run at ingestion over every detected face — 956 embeddings stored. CLIP is trained for semantic similarity and would happily match two different people who look alike in context; ArcFace is trained specifically for identity with an angular margin loss, so its embedding space separates individuals rather than scenes. They are stored in separate FAISS indexes and never mixed.
84% match — 84% of what? Is that a probability that it is the same person?
No, and I would not let anyone read it that way. It is cosine similarity in ArcFace embedding space rendered as a percentage. Our accept threshold is 0.30. The honest interpretation is ranking plus a floor, not calibrated probability — we have not run a ROC on this dataset, so I cannot give you a false-accept rate. For a real deployment that calibration is mandatory before anyone acts on a match.
How do you know these 13 hits are the same person and not 13 lookalikes?
Strictly speaking I do not have ground-truth identity labels, so I can only give you the evidence: all 13 hits are on one camera within a 14-second window, and 262 indexed faces on the other cameras — including 87 on CAM-06 and 73 on CAM-12 — scored below threshold. That is consistent with one person walking through one frame. It is not proof, and the PDF report says as much on every page.
This is face recognition on public CCTV. What stops it being abused?
Three things, and I will be honest that they are the beginning rather than the end. The report footer stamps every exported PDF with a SHA-256 and the line "Frames are AI-ranked candidates and should be verified by an investigator before use as evidence" — the tool never asserts identity. The platform is role-gated so a citizen account cannot reach this screen. And the search is per-query and logged, not a standing watchlist. What is genuinely missing is a warrant/authorisation gate and a retention policy on the face index — I would not deploy this without both.
Why is face search 560 ms when text is 80 ms?
Because the probe has to be processed first: detect the face in the uploaded image, align it, then run the ArcFace encoder, before the FAISS lookup over 956 vectors even starts. The lookup itself is negligible. Text search only has to encode a short string.
Only 956 faces from 417 frames — is the face detector missing people?
It is finding what is findable. 694 of those 956 are on CAM-07, the close-range market camera; the overhead traffic cameras contribute almost none because faces are a handful of pixels at that distance and angle. That is an honest property of the camera geometry, not a tuning problem — CCTV mounted for vehicle coverage will not give you usable faces, which is why the Scene Analytics screen reports per-camera quality separately.

If they ask

What does "5.6× fewer once tracked" actually mean?
CAM-07 has 251 person detections across its keyframes but only 45 distinct tracks. Every keyframe re-detects the same people, so the raw count massively overstates footfall — tracking links those boxes into one identity each. The 5.6× is the inflation factor you would have reported if you had naively counted detections. We show both numbers and the ratio precisely so nobody quotes the wrong one.
Your own screen says CAM-12 tracking quality is "poor". Why should I trust the 95 objects it just counted?
You should trust it less than the CAM-07 number, and that is exactly why the badge is there. Poor means 43% of detections were seen only once or twice, so the tracker is fragmenting one object into several — which inflates "distinct objects" upward. The direction of the error is knowable: on a poor-graded camera, distinct-object counts are an over-estimate and the true figure is lower. We would rather hand an investigator a graded number than a confident wrong one.
How is the quality grade computed?
Two inputs, both shown in the tooltip: keyframe density (fps estimate) and measured fragmentation — the share of detections belonging to tracks seen only once or twice. CAM-07 is good at ~2.0 fps and 13% fragmentation; CAM-01 is poor at ~0.2 fps and 100% fragmentation, because it only has 3 keyframes so every detection is its own track. It is a heuristic, not a learned metric, and it is deliberately pessimistic.
Is the tripwire counting people or detections?
Tracks. A crossing is registered when a track's bottom-centre point moves from one side of the line to the other, so one person walking through counts once regardless of how many keyframes they appear in. The event list names the track ID, which is why you see the same #11 cross out and then back in — that is one person doubling back, not two people.
Why does the crossing count change so much when I move the line?
Because it only counts tracks that actually cross that line, and the footage has strong movement corridors. On CAM-10 a line at 30% height catches 31 crossings; the same line at 60% catches 9. That is real geometry, not instability — but it does mean an operator has to place the line where the traffic is, which is why the tool is interactive rather than automatic.
What makes the PDF forensically useful rather than just a printout?
Four things. Every frame carries its camera, timestamp, frame ID and source filename, so it is traceable back to the original video. The object inventory per frame is recorded. The footer carries a SHA-256 of the document content, rendered two-pass so the hash is reproducible — re-render the same content and you get the same digest, which means tampering is detectable. And the footer states that frames are AI-ranked candidates requiring investigator verification, so the document never overstates itself.

Careful / known limits

  • The X-Integrity-SHA256 response header is never sent. build_report_with_integrity() returns the digest and integrity_headers() exists to serve it, but /api/report calls the plain build_report() and sets only Content-Disposition — the function has no caller outside report.py. The hash is still stamped in the PDF footer, so the feature works, but do not claim the API exposes it.
  • A report requested with nonexistent frame IDs returns HTTP 200 and a PDF that says "Frames in report: 1" while rendering no frames, because the count is len(frame_ids) rather than the number actually resolved. Cosmetic, but it is a forensic document making a false count claim.
  • PDF timestamps are in the container's clock/timezone, not IST. My reports generated just after midnight IST on 20 Aug are stamped "2026-08-19 19:53:48". For an evidence document the timezone matters; a judge reading the date could reasonably query it.

If they ask

What does the SHA-256 in the footer actually protect against?
Alteration of an issued document. It is a two-pass render: pass 1 builds the PDF with a blank stamp and hashes those bytes, pass 2 rebuilds the same content with that digest printed in the footer. ReportLab runs with rl_config.invariant = 1 so internal PDF timestamps and object IDs are pinned, which makes the byte stream a pure function of the content — I verified two identical requests produce byte-identical files. Be precise about the claim though: the 'Generated' timestamp is part of the hashed content, so re-rendering the same frames three seconds later gives a different hash. It seals a specific issued document; it is not a content-only fingerprint of the frames.
Could someone regenerate the PDF, change a frame, and re-stamp a matching hash?
Yes, if they control the server — the hash is self-computed, not signed by an external authority. This is tamper-evidence, not non-repudiation. Making it non-repudiable means signing the digest with a key the station doesn't hold, or anchoring it to an external timestamp authority. Neither is implemented. What it does buy you is that a PDF edited after download will no longer match its own footer.
Are the AI's bounding boxes in the report?
No, and I'd rather say so than get caught. On screen the green box is a CSS overlay positioned from normalised coordinates the API returns as match_bbox — that's why the on-screen result looks so precise. The PDF embeds the raw keyframe, so the box isn't there. What the PDF does carry instead is the full YOLO object inventory per frame in text — 'Objects: car(16), person(3), truck(2), motorcycle(1)' — so the detection evidence is present, just not drawn.
Why is the PDF creation date the year 2000?
That's ReportLab's invariant mode, and it's deliberate. Fixed internal timestamps are exactly what makes the byte output reproducible and therefore the integrity hash verifiable. The real generation time is printed in the document body and in every page footer. It does look odd in File > Properties, and while we were in there we also left author and subject as '(anonymous)' / '(unspecified)' even though we know the investigator's name — that's a genuine miss, one line to fix.
You mention an X-Integrity-SHA256 header — I don't see it.
You're right, it isn't emitted. The report service defines build_report_with_integrity() returning (bytes, digest) and an integrity_headers() helper specifically for this, but the route at backend/app/api/routes.py:393 still calls the older build_report(), which returns bytes only. How does the detection work? Is it a separate model per class?
No — it is hybrid and costs zero extra inference. Every keyframe already gets a CLIP vector for semantic search. A measured margin, not a raw threshold. A class fires only when it beats the BEST of six negative 'normal scene' prompts — 'a normal city street with traffic', 'calm traffic flowing on a road', 'people walking peacefully on a sidewalk', and so on — by a calibrated margin (default 0.03, with per-class overrides, calibrated empirically via scripts/anomaly_selftest.py). The margin is what keeps ordinary street footage at effectively zero, and the empty screen in front of you is that calibration working on 417 real frames.
Why do some alerts have a box drawn and others don't?
Because only YOLO signals are localised. CLIP scores the WHOLE frame — it tells you the scene looks like a fire, not where in the frame the fire is — so a CLIP-sourced alert has null coordinates and the card deliberately draws no box rather than inventing one. YOLO signals carry a real bounding box, stored as 0..1 frame fractions so it renders correctly at any thumbnail size. What stops a burning car generating a hundred alerts?
Debouncing per (video_id, type). A new signal joins the most recent open event of the same type on the same feed if its last grouped frame is within 30 seconds; otherwise it opens a new event. If they ask

What exactly does the forecast predict, and for when?
One 7-day window ahead, per locality, on the same 0-100 scale as the current score. predicted_score = current_score × min(growth, 2.0), capped at 100, where growth = (load in the last 7 days + 1) / (load in the 7 days before that + 1). The +1 smoothing stops empty windows exploding and the ×2 cap stops one quiet fortnight producing a nonsense number. Concretely on screen right now: SG Highway 64.9 → 87.0 rising, Bapunagar 100 → 34.9 falling, Vatva 90.8 → 84.5 stable. Across all 30 areas: 9 rising, 9 stable, 12 falling.
How do you know it predicts anything? Show me the validation.
Rolling-origin (walk-forward) temporal cross-validation, 8 weekly folds over 30 localities, first fold starting 2026-06-24 and the last 2026-08-12. For each fold we score the model with an as_of cutoff so it sees ONLY complaints strictly before the fold start, then grade it against what actually happened in the following 7 days. No future data ever reaches a prediction. Current live numbers: Hit-Rate@10 0.7818, PAI@10 2.345x, Hit-Rate@5 0.5382, PAI@5 3.229x.
What is PAI and why should I care about 2.35x?
Predictive Accuracy Index, the field standard from Chainey, Tompson & Uhlig (2008): hit-rate divided by the share of the area you are policing. PAI@10 = (crime captured in the top 10 areas / total crime) ÷ (10/30). PAI = 1 is exactly chance — you get 33% of the crime by covering 33% of the city. 2.345 means we concentrate 2.3x more crime per unit of patrol area than blind coverage. Our random baseline measured 1.053x, which is the sanity check that the metric is wired up correctly.
2.35x doesn't sound like much. Is that good?
That is the right question, and it is why we publish the oracle ceiling. If you rank each fold by its OWN realised next-week counts — perfect hindsight, the best any predictor could possibly do — PAI@10 is only 2.529x on this data. So 2.345 is 93% of the theoretical maximum. The ceiling is low because the synthetic stream is fairly stationary and lightly contrasted; on lumpier real data both numbers would rise. The honest claim is the percentage of the ceiling, not the absolute.
What are the confidence intervals and how were they computed?
90% intervals by bootstrapping over folds: resample the 8 per-fold metrics with replacement 1,000 times, take the 5th and 95th percentiles of the resampled means, fixed seed 20240601 so it reproduces exactly. Hit-Rate@10 [0.757, 0.809]; PAI@10 [2.271, 2.428]; Hit-Rate@5 [0.499, 0.577]. Pure stdlib random/math — no numpy, no sklearn, so it runs anywhere the backend does.
What do you compare against? Isn't a naive count just as good?
That is nearly true and we publish it rather than hide it. Four strategies on identical folds, PAI@10: model 2.345x, raw all-time frequency 2.220x, static prior-only 1.953x, random 1.053x. So the full model beats a naive complaint count by about 5%. Worse — and this is in our ablation doc — the stripped-down floor actually BEATS the full model at k=5 (Hit-Rate 0.552 vs 0.540). Our advantage exists at k=10 and vanishes at k=5. The headline HR@10 hides that, and I would rather say it than have you find it.

Base letters and most matras are fine; anything with ि is visibly wrong. The correct fix is a shaping engine — HarfBuzz via uharfbuzz, or rendering through WeasyPrint/Pango instead of ReportLab — which is a real piece of work, not a config flag. So today: use English for the document body. The UI, the case data and the officer's workflow are trilingual; the printed evidentiary record is English.
So a judge should not ask you to print a Hindi chargesheet.
They can, and I would show it — it will print an English body with an accurate label saying that is what happened. What I will not do is put Hindi paragraphs in an evidentiary document and let broken conjuncts go into a court file. Stamping "Language: HI" on an English document was a false statement on a record and we fixed that this morning; printing garbled Devanagari would be the same mistake wearing a different hat.
These look like Word templates with mail-merge. What is the AI part?
The document assembly is deterministic by design — you do not want a language model inventing the wording of a remand application. Two AI pieces sit around it. The section suggester scores the narrative against a curated BNS 2023 / BNSS / BSA catalogue and prints the terms that matched, so the officer sees the reasoning. And the pool itself is fed by the rest of the platform — the Face Identification Form has a slot for VisionScan's facial-match reference, similarity score and camera timestamp. The value here is not generative prose, it is that seven statutory documents share one source of truth and stay consistent with each other.
How do you know the BNS section numbers are right? Wrong sections in front of police judges are fatal.
They were cross-checked against the enacted BNS 2023, BNSS 2023 and BSA 2023 texts, and the source file says so at the top with a standing warning. Where a mapping is broad the entry carries verify=True and the UI surfaces a "verify before use" caution. Landmark judgments are attached only where squarely on point — otherwise the list is left empty rather than risk a bad cite. And the IPC cross-references are labelled as the closest pre-2023 equivalent for officer familiarity, not a claim of identical scope. Every card also carries "Always verify the exact clause against the bare act before filing."
Why did my narrative return zero sections?
Because the suggester is a deterministic substring matcher over 30 offence patterns, not a semantic model — deliberately, so it is auditable and can show you exactly which words fired. The cost is that it misses paraphrase. I measured it: "posing as a CBI officer… digital arrest… mule accounts" scores zero, because none of cheating/fraud/otp/phishing/personation/fake/scam appear. Add "online fraud" and "OTP" to the same facts and it scores 10 across three patterns. That is a real gap, and the fix is the same ChromaDB retrieval Arbiter already uses — the infrastructure is already in the repo, it just is not wired to this catalogue yet.
Where do the generated PDFs live? Can they be tampered with?
Each generation is recorded server-side with case, doc type, language, an incrementing version, the generating officer's id and a timestamp, and it writes an immutable Case Diary entry. Versions never overwrite — the chargesheet on case 29 is at v9 because I regenerated it during load testing, and all nine are in the history. What is not there yet is a content hash or signature on the stored bytes, so this is tamper-evident at the metadata level, not cryptographically tamper-proof.

How are the four roles ranked?
citizen < officer < lead < admin, compared by role_rank(). Endpoints declare a minimum: evidence and citizen-visibility need officer; case creation, closing and complaint triage need lead; user/team management, exports, system status, security events and broadcasts need admin. Reads on a case additionally pass through can_access_case(), which checks team membership, personal assignment, or complainant ownership plus the citizen-visible flag.
Can an officer from another station read this station's cases?
No — the case query filters on assigned_team_id or an explicit row in case_assignments. There is only one team in this demo database, so you have to take the query on trust or create a second team live in Admin → teams to show it.
What stops a citizen from spamming an investigating officer?
A server-side cap of one message per case: the second POST returns 403 "Citizens may send only one message per case". The UI even changes the placeholder to "One message allowed…".
If you demote someone, do their existing sessions keep working?
No. PATCH /api/users/{id} bumps that user's token_version whenever role or active changes, and every JWT carries the version it was minted with, so all outstanding tokens for that user stop validating immediately. The same mechanism backs the "Sign out all my sessions" button.
